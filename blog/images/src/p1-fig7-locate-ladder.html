What one anchor is worth
The scores are a confidence ladder, not a ranking of files. A definition beats a usage, a usage beats a mention of the same string.
Strongest evidence first: the code that defines the thing your anchor names.
100
compose-definition@Composable InputBar
The composable itself, matched by name or by the line the inspector reported.
90
compose-locationfile from the inspector
The inspector named the file but not a composable that resolves, so the file stands in.
80
id-usage-strongR.id near a listener
An id reference that sits in a file which also wires up a click listener.
78
layout-id<View android:id>
The layout that defines the id. Geometry and label usually live here.
Weaker: the anchor appears, but the line may be a duplicate of the real one.
48
literal-textText("发送")
A string literal on a Text/Button/setText line. Two stages can both match it.
45
compose-callsiteInputBar( … )
Whoever calls the composable. Useful for the tree, not for the handler.
$ android-layout locate-code --compose-name InputBar --text 发送 100 …/stage1/ui/ChatScreen.kt:163 [compose-definition] @Composable InputBar definition 48 …/stage1/ui/ChatScreen.kt:184 [literal-text] Text("发送") 48 …/stage2/ui/ChatScreen.kt:108 [literal-text] Text("发送") 45 …/stage1/ui/ChatScreen.kt:103 [compose-callsite] Calls InputBar
Ties break by path, then by line, so the same anchor produces the same order twice. `locate_code` ranks files and stops there: opening the file is still the agent's job.
